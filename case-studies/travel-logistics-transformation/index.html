Case Study

Global Travel Logistics Operations Transformation

From fragmented, manually coordinated fulfilment to a unified booking platform, integrated OMS/TMS, distributor APIs, automated dispatch, event-driven status updates and exception-led operations.

Business Transformation Process Redesign OMS / TMS API Integration Applied AI Service Operations
Interactive Operations Control Tower

Use synthetic orders to test the target operating model: deterministic validation, structured supplier dispatch and fallback, event-driven fulfilment, exception handling, AI-assisted case support and human approval.

Transformation objective

Redesign the end-to-end travel-logistics operation so that orders from direct and distributor channels enter one controlled operating system, routine decisions and status updates are automated, suppliers execute against structured jobs, and CS / Operations focuses primarily on exceptions.

As-Is boundary Customer books through the direct website or an OTA / distributor channel → service is fulfilled → final handover evidence is recorded.
To-Be ambition Establish a dedicated booking experience and operational system of record, while integrating distributors, logistics partners, payments and communication channels through APIs and lightweight partner interfaces.

Success measures

Manual touchpoints per booking
Operations handling time per booking
Exception-resolution time
SLA adherence and customer-update latency

Baseline values remain TBD until measured from operational data.

Before — current operating model

Core pattern
Customer / OTA→ Email / OTA backend→ CS / Operations→ legacy commerce platform / shared spreadsheet→ Email / supplier chat→ Supplier / Driver
Manual order normalization Distributor bookings may require CS to log into an OTA backend, retrieve booking details, validate them, and manually recreate the order through the legacy internal booking flow.
CS as communication relay Customers communicate through email / customer messaging while suppliers use email, partner messaging channels. CS manually moves status information between both sides.
Manual supplier dispatch Supplier choice depends on staff knowledge or spreadsheets. Orders are manually cleaned, forwarded, confirmed and chased across multiple channels.

Representative current-state journey

StageCurrent activity
Booking intakeDirect website bookings arrive through the legacy commerce platform. OTA orders arrive through email and distributor backends.
Internal order creationDistributor order information may be copied manually into the direct booking flow to create the internal record.

Supplier confirmationSupplier replies by email; missing confirmations may be chased in partner messaging groups.

What the diagnosis showed

Fragmented system of record Order state is distributed across the e-commerce layer, shared spreadsheets, shared email, OTA systems, messaging tools and supplier channels.
Tacit operational knowledge Important exception logic, routing preferences and contextual judgement are not fully represented as maintained system rules.
Key-person dependency Non-standard decisions frequently require escalation to experienced Operations staff.
No structured dispatch control loop Assignment, acceptance, non-response, fallback and service-day status do not run through one controlled workflow.
Design implication

The target state should not merely automate email forwarding. It needs a proper transaction core: one booking / shipment record, a lifecycle state model, a maintained rules layer, structured partner execution and an exception-management workspace.

After — target operating model

The recommended future state follows the way modern logistics and commerce platforms separate the customer channel, transaction core, integration layer, partner execution and exception-management functions.

1 · Customer booking layer
Responsive web booking Serviceability check Dynamic service options Payment gateway Secure tracking link

Provide a dedicated booking experience and booking API. Keep commodity services such as payment processing external rather than rebuilding them.

2 · Distributor integration layer
REST APIs Webhooks Scheduled API sync CSV / email fallback adapters Canonical data mapping

Distributor and OTA channels should create or update orders directly in the internal platform without manual re-entry wherever integration capability exists.

3 · OMS / TMS core — system of record
Canonical Order ID Customer & itinerary Shipment / bag records Status state machine SLA timestamps Supplier assignment Fees / adjustments Exception state Audit history

Every booking, regardless of source, resolves to one structured record. Email becomes a notification channel rather than the operational database.

4 · Rules & master-data layer
Service areas Airport timing rules Lead times Supplier capabilities Route eligibility Pricing references Escalation rules Version history

Move repeatable operating rules out of memory and scattered spreadsheets into maintained configuration that the workflow can execute.

5 · Dispatch & partner execution
Supplier ranking Auto-dispatch Accept / reject timer Fallback supplier Manual override Partner API Partner portal / secure job link

Mature partners can integrate by API; smaller partners can use a lightweight mobile web interface or secure job link. A dedicated driver app is not mandatory.

6 · Event-driven communication
Booking confirmed Supplier assigned Customer ready Picked up Delivered Delay / exception Email Messaging integration

Customers receive status automatically from structured events. CS no longer has to manually relay routine “arrived”, “picked up” or “delivered” messages.

7 · Exception control tower
Exception queue Severity / priority Owner SLA clock Recommended action Escalation Resolution log

CS / Operations shifts from monitoring every normal order to managing only cases that require intervention.

8 · Chain of custody & proof of service
Pickup evidence Bag / tag ID Recipient verification OTP / QR where appropriate Delivery evidence Timestamp / location metadata

Proof should establish not only that a handover happened, but that it occurred to the correct party.

9 · Data, analytics & process intelligence
Event log Cycle time Manual touchpoints Supplier acceptance SLA adherence Exception rate Customer update latency

A structured event history makes operational performance measurable and enables process mining rather than relying on anecdotal diagnosis.

10 · AI assistance layer
Intent extraction Missing-information detection Exception classification Knowledge retrieval Case summarization Response drafting

AI assists around the transaction core. It should not be the source of truth and should not autonomously approve high-risk policy, payment or recipient-verification decisions.

11 · Governance & access control
Role-based access PII controls Audit log Rule ownership Change history Human override

Core platform vs integrated services

Core platform Booking UX and booking API; OMS/TMS transaction core; canonical data model; lifecycle state; rules and supplier master data; dispatch logic; exception workspace; operational event log; chain-of-custody controls.
Integrate rather than rebuild Payment processing, email delivery, messaging providers, mapping / geocoding, OTA channels, mature logistics-partner APIs, identity / OTP services and analytics tooling where appropriate.

Human vs Automation vs AI decision matrix

The target model separates work by decision type rather than applying AI everywhere. Deterministic rules handle repeatable operational logic, AI handles ambiguity and unstructured information, and humans retain control where judgement, policy, safety or commercial authority is required.

Decision rule

Automate when the input is structured and the rule is stable. Use AI when the input is unstructured or contextual. Keep a human in control when the decision is high-risk, policy-sensitive, irreversible or commercially discretionary.

Process step Primary owner Role of automation Role of AI Human control / guardrail
Direct / OTA booking ingestion Automation Create canonical order, map fields, deduplicate, assign source and timestamps. Fallback extraction when source data arrives in semi-structured email or documents. CS reviews failed mappings or incomplete orders.
Serviceability & timing validation Automation Execute city, lead-time, airport timing, product-type and required-field rules. Interpret ambiguous addresses or customer-written notes when structured validation is insufficient. Operations approves unclear or policy-edge cases.
Missing-information follow-up Automation + AI Detect missing required fields and trigger follow-up workflow. Draft context-aware request using order history and customer language. Human review only for non-standard or sensitive cases.
Supplier eligibility & ranking Automation Filter by service area, capability, timing, route, cost rules and availability; rank eligible suppliers. Optional explanation of why a route is unusual or why historical supplier behavior differs. Operations can override assignment with reason captured.
Supplier dispatch Automation Generate structured job, send through API / portal / secure link, start acceptance timer, trigger fallback. No AI required for normal dispatch. Human intervention for no-capacity, RFQ or special-service cases.
Supplier confirmation & reminder Automation Track accept / reject / timeout state and send reminders or escalate automatically. Interpret free-text supplier replies if structured response is unavailable. Operations resolves ambiguous replies.
Customer service-day updates Automation Trigger notifications from structured events such as ready, picked up, delayed and delivered. Adapt wording / language and summarize relevant context. CS handles complaints, disputes or unclear status.
Inbound customer messages AI + Automation Attach message to correct order and route to workflow. Classify intent, extract requested change, detect urgency, summarize conversation and retrieve relevant rule. CS approves actions that alter service, fees or policy.
Operational exception triage AI-assisted Human Create case, start SLA clock, collect order / supplier / customer context. Classify exception, summarize evidence, retrieve playbook and propose next action. Operations makes the actual exception decision.
Fee waiver / refund / policy exception Human Calculate standard entitlement where rules are explicit. Summarize case and surface comparable precedent. Authorized manager approves discretionary outcome.
Chain of custody / recipient handover Automation + Human control Use OTP / QR / tag verification, timestamps and evidence requirements. Optional photo-quality or evidence-completeness checks. AI does not independently decide recipient identity or release the shipment in high-risk cases.
Knowledge retrieval AI Maintain versioned rule and supplier data sources. Retrieve the most relevant operational rule, supplier condition or exception playbook for the current case. Responses must cite the governed source; staff can escalate conflicting rules.
Performance monitoring Automation Calculate SLA, cycle time, rework, acceptance, exception and communication-latency metrics. Summarize recurring patterns and highlight anomalous process variants. Managers validate conclusions before changing policy or supplier strategy.

AI guardrails

AI is not the system of recordThe OMS/TMS is the authoritative source for booking state, financial status, supplier assignment and operational timestamps.
Structured rules beat AI where possibleServiceability, time windows, pricing formulas and eligibility should be deterministic when the policy is known.
Ground AI in governed knowledgeOperational answers should retrieve from maintained rules, supplier data and approved playbooks rather than rely on model memory.
Escalate uncertaintyLow-confidence extraction, conflicting rules, policy exceptions and safety-sensitive decisions route to a human.

Requirements — Booking Intake & Normalization

This first requirements slice translates the target architecture into implementation-ready business analysis for the point where direct and distributor bookings enter the operating system.

Business requirements

IDRequirementBusiness rationale
BR-01 All direct and distributor bookings must resolve to one canonical internal order record. Remove duplicate manual order creation and create one source of truth for downstream operations.
BR-02 The booking source must not determine how Operations processes the order after normalization. Direct website, distributor and future channels should enter the same fulfilment workflow once mapped.
BR-03 Routine booking ingestion and validation should require no CS intervention when required data is complete and rules are satisfied. Move CS effort away from data entry and toward true exceptions.
BR-04 No booking may disappear silently between an external channel and the internal OMS/TMS. Every ingestion attempt must have an auditable success, exception or failure state.
BR-05 Channel-specific differences must be absorbed by the integration layer rather than by frontline staff. Reduce process variation, training burden and transcription risk.

Functional requirements

IDSystem behavior
FR-01The platform shall accept direct bookings from the customer booking interface and distributor bookings through API, webhook, scheduled sync or controlled fallback ingestion.
FR-02The integration layer shall map each source schema into a canonical order model before the order enters fulfilment.
FR-03The platform shall generate one unique internal Order ID and preserve the original external source and external Order ID.
FR-04The platform shall prevent duplicate creation when the same external booking is received more than once.
FR-05The platform shall validate required fields such as service date/time, city, service type, customer identity/contact details, pickup/delivery location, and route-specific airport/flight information where applicable.
FR-06The platform shall run deterministic serviceability and timing rules immediately after normalization.
FR-07Orders that pass validation shall progress automatically to the next fulfilment state without manual re-entry.
FR-08Orders with missing, conflicting or non-compliant data shall enter a structured exception queue with the failed rule and required next action.
FR-09Where source data arrives in semi-structured email or documents, AI-assisted extraction may propose field values, but low-confidence or conflicting fields must require human confirmation.
FR-10Every create, update, validation result, exception and manual override shall be timestamped in the audit history.

Canonical data requirements

Order identity Internal Order ID, source channel, source Order ID, booking timestamp, current lifecycle status.
Customer Name, email, contact number, preferred communication channel / app where captured.
Service Service date, service time, city, service type, pickup type, delivery type.
Locations Hotel / property name, address, airport, terminal, relevant location notes.
Travel context Flight number and route-specific timing information where applicable.
Operational metadata Validation result, failed rule, assigned supplier, SLA timestamps, exception status and audit trail.

Non-functional requirements

IDRequirement
NFR-01Reliability: ingestion must be retryable and idempotent so retries do not create duplicate orders.
NFR-02Observability: failed integrations, schema-mapping errors and validation failures must be visible in an operational dashboard / queue.
NFR-03Auditability: the system must retain who/what changed an order, the previous value, the new value and timestamp.
NFR-04Security: customer PII must be role-restricted, and integrations must use controlled credentials rather than personal accounts.
NFR-05Maintainability: source mappings and business rules should be configurable without rewriting the full application wherever practical.
NFR-06Extensibility: adding a new distributor should require a new adapter / mapping, not a new fulfilment process.
NFR-07Performance: normal automated booking ingestion and validation should complete within an agreed operational threshold; exact SLA to be defined during implementation.

Acceptance criteria

AC-01 · Website bookingA valid direct booking creates exactly one canonical OMS/TMS order with the correct source metadata and proceeds without CS re-entry.
AC-02 · Distributor bookingA valid distributor booking produces the same canonical internal structure as a direct booking while preserving the distributor Order ID.
AC-03 · Duplicate eventReceiving the same external booking twice updates or ignores the duplicate according to policy and never creates a second active order.
AC-04 · Missing fieldA booking missing a required contact / route field is stopped before dispatch and appears in the exception queue with a clear reason.
AC-05 · Rule failureA booking outside a configured service area or timing rule does not progress silently and is routed to the correct exception workflow.
AC-06 · Audit trailAn Operations user can reconstruct how the booking entered the system, what validation ran, what changed and who approved any override.

Representative UAT scenarios

ScenarioGivenWhenThen
UAT-01 · Happy-path direct booking All mandatory website fields are valid. Customer completes payment and booking. One canonical order is created, validation passes and the order advances automatically.
UAT-02 · Happy-path distributor booking A distributor sends a complete supported booking payload. The integration receives it. Fields are mapped correctly, the external Order ID is retained, and no CS copy/paste is required.
UAT-03 · Missing flight information An airport-related booking requires flight data but the source does not supply it. Validation runs. The order enters the exception queue and a missing-information workflow is triggered.
UAT-04 · Duplicate OTA delivery An external channel retries the same booking event. The same source Order ID is received again. No duplicate active order is created and the event is logged.
UAT-05 · Non-serviceable address The destination fails the configured service-area rule. Validation runs. The booking is held, the failed rule is visible, and Operations is given the appropriate resolution path.
UAT-06 · AI extraction uncertainty A fallback email contains an ambiguous hotel address. AI-assisted extraction returns low confidence or conflicting candidate values. The system does not auto-approve the field and requires human confirmation.

Control design

Normal flow should be touchless; uncertainty should be visible.

The objective is not to remove humans from operations. It is to make routine orders deterministic and auditable so human attention is concentrated on incomplete, ambiguous, non-compliant or high-risk cases.

Requirements — Supplier Dispatch & Assignment

This requirements slice converts supplier selection and dispatch into a controlled workflow with explicit eligibility rules, ranked assignment, acknowledgement states, timeout handling and auditable human override.

Business requirements

IDRequirementBusiness rationale
BR-D01 Every serviceable order must have a clearly identified supplier-assignment state before execution. Remove reliance on informal memory and make unassigned orders visible before service day.
BR-D02 Supplier selection should be based on maintained operational criteria rather than staff memory alone. Improve consistency and reduce key-person dependency.
BR-D03 Routine fixed-supplier orders should be dispatched automatically where the assignment rule is deterministic. Eliminate repetitive email preparation and forwarding work.
BR-D04 Non-response, rejection and unavailable capacity must trigger a defined fallback path before the service SLA is at risk. Replace passive follow-up with proactive exception control.
BR-D05 Operations must retain authority to override an automated assignment when contextual judgement is required. Preserve operational flexibility for special routes, exceptions and supplier-specific circumstances.

Functional requirements

IDSystem behavior
FR-D01The OMS/TMS shall maintain a supplier master containing service areas, route capabilities, operating windows, contact / integration method, priority, commercial reference and active / inactive status.
FR-D02The system shall filter suppliers using deterministic eligibility rules before ranking candidates.
FR-D03The system shall support configurable supplier-priority logic by market, route, service type and other maintained criteria.
FR-D04For a deterministic fixed-supplier route, the system shall create a structured dispatch job automatically when the order becomes dispatch-ready.
FR-D05Dispatch payloads shall contain only the information required for fulfilment and shall exclude internal pricing, internal notes and other non-required sensitive fields by design.
FR-D06The dispatch channel shall be selected according to partner capability: API for integrated partners, partner portal / secure job link for supported partners, and controlled email fallback where necessary.
FR-D07The system shall record supplier responses using explicit states such as Sent, Accepted, Rejected, Timed Out and Cancelled.
FR-D08Each dispatched job shall have a configurable acknowledgement deadline appropriate to the service date and market.
FR-D09If the preferred supplier rejects or times out, the system shall evaluate the next eligible supplier or create an Operations exception when automatic fallback is not permitted.
FR-D10Operations shall be able to manually override supplier assignment, with the reason and user recorded in the audit log.
FR-D11Special / RFQ routes shall bypass automatic final assignment and enter a structured quote workflow.
FR-D12The system shall surface all orders without confirmed supplier assignment within a configurable pre-service risk window.
FR-D13Free-text supplier responses received through fallback channels may be interpreted by AI for suggested status classification, but ambiguous replies shall require human confirmation.

Supplier master & dispatch data

Supplier identity Supplier ID, legal / operating name, country / market, active status, primary operational contact.
Capability Service areas, airports, route types, service windows, bag / vehicle constraints, special handling capability.
Routing controls Priority, preferred routes, fallback order, exclusion rules, manual-only flags.
Commercial reference Agreed pricing reference or RFQ-required flag. Commercial data remains access-controlled.
Integration method API, portal / secure link, email fallback, supported response method and acknowledgement timeout.
Performance history Acceptance rate, response time, cancellation / rejection patterns, SLA performance and exception history where available.

Non-functional requirements

IDRequirement
NFR-D01Configurability: supplier eligibility, priority and timeout rules should be changeable by authorized Operations users without code deployment where practical.
NFR-D02Auditability: every automated or manual assignment decision must record the candidate set, selected supplier, rule / override reason and timestamp.
NFR-D03Privacy: dispatch payloads must follow data-minimization principles and expose only fields needed by the supplier.
NFR-D04Resilience: failed partner API calls must retry safely and fall into a visible exception state rather than silently losing the job.
NFR-D05Interoperability: the dispatch model should support both integrated and low-tech suppliers without creating a separate internal fulfilment process for each.
NFR-D06Observability: Operations must be able to see assignment status, acknowledgement deadlines, overdue confirmations and fallback actions in one view.

Acceptance criteria

AC-D01 · Fixed routeA valid order on a deterministic fixed-supplier route is dispatched to the correct supplier without staff searching a spreadsheet or manually editing an email.
AC-D02 · Data minimizationThe supplier receives the operational fields required for fulfilment but not internal pricing or restricted internal content.
AC-D03 · AcceptanceWhen the supplier accepts, the OMS/TMS records the acceptance timestamp and changes the booking assignment state to Confirmed.
AC-D04 · RejectionWhen the supplier rejects, the system evaluates the configured fallback path and does not leave the booking in an apparently assigned state.
AC-D05 · TimeoutIf acknowledgement is not received by the configured deadline, the booking becomes visible in the exception queue and the fallback / escalation policy runs.
AC-D06 · Manual overrideAn authorized Operations user can assign a different supplier and the system retains the original recommendation plus override reason.

Representative UAT scenarios

ScenarioGivenWhenThen
UAT-D01 · Normal fixed-supplier dispatch A validated order matches a configured fixed-supplier route. The order reaches Dispatch Ready. The system creates the job, sends it through the supplier’s supported channel and starts the acknowledgement timer.
UAT-D02 · Supplier accepts A dispatch job is waiting for acknowledgement. The supplier returns an Accept response. The order becomes Assigned / Confirmed and the acceptance timestamp is recorded.
UAT-D03 · Supplier rejects A second eligible supplier exists. The preferred supplier rejects the job. The system applies the configured fallback path or surfaces the case for Operations if auto-fallback is disabled.
UAT-D04 · No supplier response The acknowledgement deadline expires. No valid response has been received. The system marks the job Timed Out, triggers fallback / escalation and flags the booking as a pre-service risk.
UAT-D05 · Special RFQ route The route is marked RFQ Required. The order reaches Dispatch Ready. No supplier is automatically confirmed; the order enters the quote workflow with the required route information.
UAT-D06 · Ambiguous email response A non-integrated supplier replies “should be okay, will confirm later.” AI-assisted classification evaluates the message. The system does not record Accepted automatically and routes the ambiguous response to Operations.

Control design

Automate the routing logic; preserve accountable override.

The objective is not to remove Operations from supplier management. It is to convert routine assignment into an explicit, measurable control loop and reserve human attention for capacity problems, RFQs, unusual routes and contextual exceptions.

Requirements — Service-Day Communication & Exception Management

This slice redesigns the highest-touch part of the current operation: routine status relaying, multi-channel service-day communication and exception firefighting. The target state is event-driven for normal execution and exception-led for human intervention.

Business requirements

IDRequirementBusiness rationale
BR-C01 Routine service-day status updates should not require CS to manually relay information between customer and supplier / driver. Reduce manual touchpoints and customer-update latency.
BR-C02 All service-day communication must remain linked to the correct order and current execution state. Prevent context loss across email, messaging and supplier channels.
BR-C03 Exceptions must be converted into explicit cases with owner, severity, SLA clock, required action and resolution history. Replace ad hoc firefighting with a controlled exception-management process.
BR-C04 AI may assist with interpretation and triage, but high-risk operational, payment, policy and handover decisions must remain human-controlled. Use AI where it adds speed without allowing uncertain model output to become an uncontrolled operational action.
BR-C05 Operations must be able to reconstruct the complete service-day timeline from booking state, messages, supplier events and human decisions. Create auditability and support later process-intelligence analysis.

Functional requirements

IDSystem behavior
FR-C01The OMS/TMS shall record structured execution events such as Customer Ready, Driver En Route, Pickup Attempted, Picked Up, Delivery Attempted, Delivered, Waiting, Delayed and Exception Raised.
FR-C02Configured events shall automatically trigger the appropriate customer notification through the available customer communication channel.
FR-C03Supplier / driver status updates received through API, portal, secure link or controlled fallback channels shall update the same canonical order timeline.
FR-C04Inbound customer messages shall be matched to the correct booking using available identifiers such as Order ID, verified email, contact number and conversation context.
FR-C05AI may classify inbound messages into intents such as timing change, arrival / readiness, missing information, delay inquiry, complaint, pickup issue, delivery issue or cancellation request.
FR-C06AI may extract proposed structured updates from customer or supplier messages, but changes affecting service time, location, fees or policy must follow the relevant validation and approval workflow.
FR-C07The system shall create an exception case automatically when a defined risk condition occurs, including unresolved pickup, delivery rejection, excessive waiting, SLA risk, supplier non-response or conflicting order information.
FR-C08Each exception case shall store category, severity, owner, SLA timer, related order, evidence, relevant rule / playbook, current status and resolution history.
FR-C09AI may generate a concise case summary from order state, conversation history, supplier messages and prior actions.
FR-C10AI may retrieve the relevant approved operational rule or exception playbook and propose the next action, with the source displayed to the user.
FR-C11The system shall require explicit human approval before discretionary fee waivers, refunds, compensation outside fixed rules, policy overrides or safety-sensitive release decisions.
FR-C12When an exception is resolved, the resolution, responsible user and resulting order state shall be written back to the operational timeline.
FR-C13Repeated unresolved or high-severity cases shall escalate according to configurable thresholds rather than relying on individual staff memory.
FR-C14All customer-facing AI-drafted messages must be generated from the current order state and approved knowledge context; the system must not fabricate operational status.

Exception taxonomy

Pickup Customer late / unreachable, wrong meeting point, items not deposited, items not found, hotel release issue.
Delivery Wrong / changed address, guest not found, hotel rejection, no reception, property unavailable, redelivery required.
Supplier No confirmation, rejection, late driver, capacity issue, status conflict, execution failure.
Travel / external Flight disruption, road closure, severe weather, carrier compliance issue, rerouting requirement.
Customer-service Timing change, cancellation, complaint, compensation request, fee dispute, policy exception.
Chain of custody Recipient mismatch, missing proof, unclear handover evidence, unverified release.

AI context package

Before AI is asked to classify, summarize or recommend an action, the orchestration layer should assemble a bounded case context rather than passing an entire unfiltered mailbox or chat history.

Current order stateService type, route, service time, source channel, supplier, SLA state and current lifecycle status.
Relevant conversationOnly messages linked to the case / order, with sender and timestamp preserved.
Execution eventsPickup, delivery, waiting, delays, evidence and supplier acknowledgements.
Governed knowledgeApplicable service rule, supplier condition, fee rule and approved exception playbook.

Non-functional requirements

IDRequirement
NFR-C01Traceability: every automated notification, AI recommendation and human decision must be tied to the order and timestamped.
NFR-C02Explainability: AI-assisted recommendations must display the retrieved rule / playbook or evidence used to support the suggestion.
NFR-C03Confidence control: low-confidence classification or extraction must fall back to human review rather than auto-execution.
NFR-C04Channel resilience: failure of one communication channel must be visible and support an approved fallback path.
NFR-C05Latency: service-critical execution events should generate customer / Operations visibility within an agreed threshold; exact SLA to be defined during implementation.
NFR-C06Access control: policy overrides, compensation, refunds and sensitive customer data must be restricted by role.
NFR-C07Version control: AI retrieval must use the current approved version of operational rules and retain the rule version used for each decision.

Acceptance criteria

AC-C01 · Routine updateWhen a structured pickup event is recorded, the customer receives the configured pickup notification without CS manually forwarding the supplier message.
AC-C02 · Customer readinessWhen a customer reports arrival at the meeting point, the message is linked to the correct order and the relevant execution state / supplier notification is triggered or presented for confirmation.
AC-C03 · Exception creationAn unresolved pickup or delivery failure creates an exception case with owner, severity and SLA clock rather than remaining only inside chat history.
AC-C04 · AI summaryThe Operations user can open an exception and receive an accurate summary of order state, recent messages, evidence and actions without losing source traceability.
AC-C05 · Policy controlAn AI recommendation cannot independently execute a discretionary refund, fee waiver or policy override.
AC-C06 · ClosureResolving an exception updates the canonical order state and records who resolved it, what action was taken and when.

Representative UAT scenarios

ScenarioGivenWhenThen
UAT-C01 · Customer arrives at meeting point An airport pickup order is active. The customer messages “I’m at the meeting point.” The message is matched to the order, intent is classified as Customer Ready, the event is recorded and the supplier workflow is updated without requiring manual copy / paste.
UAT-C02 · Driver confirms pickup The supplier has accepted the job. The driver records pickup. The OMS/TMS changes the order state to Picked Up and sends the configured customer notification automatically.
UAT-C03 · Origin handover item not found The service partner reports that the shipment cannot be located at the handover point. The event is submitted. An exception case is opened, relevant order / storage information is assembled and the appropriate pickup playbook is presented to Operations.
UAT-C04 · Ambiguous timing request A customer sends a free-text message that may imply a timing change. AI extracts a proposed new time with low confidence. The system does not alter the booking automatically and requests human confirmation.
UAT-C05 · Fee waiver request A customer disputes a waiting fee. AI summarizes the case and retrieves the applicable waiting policy. The authorized human decides whether to apply or waive the fee; AI does not execute the financial decision.
UAT-C06 · Wrong recipient risk A Hotel → Airport handover requires customer collection. Recipient verification fails or evidence is incomplete. The shipment is not released under the automated flow and the case is escalated for human resolution.
UAT-C07 · Conflicting channels The customer emails one update while sending a different message through customer messaging platform. Both messages are linked to the same active order. The case timeline preserves both sources and flags the conflicting operational instruction for review.

Control design

Automate normal execution; make abnormal execution impossible to ignore.

The target state removes CS from routine message relaying while giving Operations a structured control tower for cases that genuinely need judgement. AI improves speed by reading, summarizing and retrieving context, but authority remains explicit and auditable.

Governance principle

The system should make accountability clearer, not hide it behind automation.

Every important operational outcome should be attributable to a maintained rule, a verified external event, a governed AI recommendation or an identifiable human decision. That is what turns automation into an enterprise operating model rather than another collection of scripts.

Implementation Roadmap

The target state should be delivered in dependency order. The sequence deliberately establishes the transaction core and operational data first, then layers integrations, workflow automation, AI assistance and process intelligence on top.

Sequencing principle

Do not start with an AI agent. First establish a reliable system of record, explicit lifecycle states and governed rules. AI becomes valuable only after the underlying process can expose accurate context, events and decision boundaries.

Phase 0 — Process & Data Foundation

Scope Finalize canonical order / shipment model, lifecycle states, exception taxonomy, supplier master, service rules and data ownership.
Key outputs BPMN To-Be, data dictionary, state model, rules catalogue, supplier master schema, integration inventory and prioritized backlog.
Dependencies Operations SME access, representative historical orders, current supplier rules and channel examples.
Exit criteria Core entities and states are agreed; critical rules have named owners; representative orders can be expressed cleanly in the canonical model.

Phase 1 — Booking + OMS/TMS Core

Scope Build the booking layer and transaction core for direct bookings: canonical Order ID, shipment records, lifecycle states, audit trail, structured validation and exception queue.
Key outputs Booking API, OMS/TMS database, order-management UI, validation engine, event log and role-based access.
Dependencies Phase 0 data model and rules; payment integration; authentication / access design.
Exit criteria A normal direct booking can move from booking to dispatch-ready without shared spreadsheet re-entry, with all state transitions and overrides auditable.

Phase 2 — Distributor Integration

Scope Connect distributor channels to the canonical order model using APIs, webhooks or scheduled sync; retain controlled fallback adapters for unsupported channels.
Key outputs Source adapters, schema mapping, deduplication, retry handling, integration monitoring and source-order traceability.
Dependencies Stable OMS/TMS create/update APIs and canonical schema.
Exit criteria Supported OTA bookings create the same internal order structure as direct bookings with no routine manual copy / paste.

Phase 3 — Supplier Dispatch & Partner Execution

Scope Implement supplier eligibility, ranking, structured dispatch, acceptance timers, fallback routing and partner response capture.
Key outputs Supplier master UI, routing rules, API / partner portal / secure-link dispatch, acknowledgement workflow and pre-service risk queue.
Dependencies Reliable order state, supplier master data and maintained routing rules.
Exit criteria Routine fixed-supplier jobs can be assigned and confirmed without staff searching spreadsheets, editing emails or manually chasing normal confirmations.

Phase 4 — Event-Driven Service-Day Operations

Scope Replace routine CS relay work with structured execution events, automated customer notifications and a central exception control tower.
Key outputs Service-day event model, notification workflows, exception queue, SLA timers, escalation rules and structured proof-of-service capture.
Dependencies Supplier execution events, canonical order timeline and communication-channel integrations.
Exit criteria Routine Ready / Picked Up / Delivered updates reach customers automatically, while unresolved exceptions appear with owner, severity and SLA state.

Phase 5 — AI-Assisted Operations

Scope Add AI where unstructured context or judgement-support creates leverage: message interpretation, field extraction, case summarization, knowledge retrieval and response drafting.
Key outputs Governed retrieval layer, evaluation dataset, prompt / model versioning, confidence thresholds, shadow-mode workflow and human-approval controls.
Dependencies Stable OMS/TMS context, governed knowledge base, audit trail and exception workflows.
Exit criteria AI reaches defined quality thresholds on representative test sets; high-risk actions remain human-controlled; production usage is traceable to source context and model / prompt version.

Phase 6 — Process Intelligence & Continuous Improvement

Scope Use structured event data to identify variants, bottlenecks, rework, supplier performance and emerging exception patterns.
Key outputs Operational dashboards, process-mining views, supplier scorecards, SLA analysis, exception trend analysis and improvement backlog.
Dependencies Consistent event logging across the preceding phases.
Exit criteria Management can measure process performance from system data rather than reconstructing it manually from email, chat and spreadsheets.

Business Case & Value Realization

The business case should be evidence-led rather than built on invented savings. The first objective is to instrument the current process, establish a reliable baseline and then measure whether the new operating model reduces human effort, errors, latency and service risk.

Value principle

Do not claim ROI before the baseline exists. Define the value equations first, collect the required operating data, then compare the pilot against the current-state control period.

Value hypothesis

1 · Reduce manual handling Remove duplicate order entry, email sanitization, routine status relaying, confirmation chasing and repetitive rule checks.
2 · Reduce error & rework Lower transcription mistakes, missed fields, wrong supplier routing, duplicated records and inconsistent exception handling.
3 · Improve service reliability Detect unconfirmed suppliers, incomplete orders and SLA risks earlier rather than discovering them close to service time.
4 · Improve customer communication Reduce the delay between an operational event and the customer receiving a reliable status update.
5 · Increase operational capacity Allow the same team to support more bookings by shifting human effort from normal-flow coordination to exceptions.
6 · Build decision-quality data Create an event-level history that supports supplier management, process improvement and future AI evaluation.

ROI model

The model separates productivity value from directly avoided cost so that capacity creation is not incorrectly presented as immediate cash savings.

Capacity value (As-Is handling minutes − To-Be handling minutes) × annual booking volume × loaded staff cost per minute
Avoided rework cost (As-Is error/rework rate − To-Be rate) × annual volume × average handling/recovery cost per incident
Avoided service-recovery cost Reduction in attributable refunds + compensation + redelivery + emergency handling cost
Incremental capacity contribution Additional bookings supported without equivalent headcount growth × contribution margin per booking
Annual quantified benefit

Capacity value + avoided rework + avoided recovery cost + validated incremental contribution

Net annual benefit

Annual quantified benefit − annual incremental run cost

Payback period

One-time implementation cost ÷ average monthly net benefit

Capacity value should be described as capacity released unless the business can demonstrate an actual reduction in labor spend. Revenue / contribution uplift should only be included if additional volume or retention can be evidenced.

Value-realization principle

The transformation is successful only if the operating metrics move.

A polished system or AI demo is not the outcome. The outcome is fewer manual touches, faster and more reliable execution, earlier risk visibility, stronger control and measurable capacity released back to the operation.
